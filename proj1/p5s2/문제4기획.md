좋아. 지금 코드의 **설계/클래스/함수/원리**를 “무엇을 어디서 왜” 하는지 관점으로 정리해줄게.

# 1) 전체 설계 개요

* **표현(표시)와 평가(연산) 분리**

  * 표시식엔 `x`, `÷`, `π`, `²/³/%` 같은 “보이는 기호”를 씀.
  * 평가 직전에만 `x/×→*`, `÷→/`로 치환 → 파서는 오직 `+ - * / ( )`, NUM, CONST, FUNC, POST만 이해.
* **엔진과 UI 분리**

  * `Calculator`/`EngineeringCalculator`가 **수학 엔진** (파싱+평가).
  * `MainWindow`가 **입력/표시/UX 상태** 담당 (버튼 라우팅, 폰트, Ans 시드, 암시적 곱셈 등).
* **UI 고정 규칙 기반 자동 라우팅**

  * 버튼 id 규칙(`btnn_*`: 숫자, `btno_*`: 일반/시스템, `btnf_*`: 공학 함수)을 이용해
  * 딕셔너리 `_handlers`를 **자동 구성**: `id → 함수` (숫자/점/삼각·쌍곡만 선점, 나머지는 `do_<tail>` 규칙).

# 2) 주요 클래스 역할

## Calculator (엔진 추상층)

* **책임**: 파이프라인 구현(토큰화 → 단항마이너스 보정 → 셔닝야드(RPN) → 스택 평가).
* **훅(Hooks)**:

  * `apply_function(name, x, angle_mode_rad)`: sin/cos 같은 **단항 함수**를 엔진이 모른 척하고 하위에 위임.
  * `apply_postfix(op, a)`: ²/³/% 같은 **후위 연산** 위임.
  * `const_value(name)`: `pi` 같은 **상수** 위임.
* **메모리 연산**(MC/MR/M+/M-), **Ans(last\_result)** 보관도 여기서 담당.

## EngineeringCalculator (엔진 구체화)

* **책임**: 공학 기능 실제 구현.

  * `const_value('pi') → math.pi`
  * `apply_function`: `sin/cos/tan/sinh/cosh/tanh` (Deg 모드면 입력각을 라디안 변환)
  * `apply_postfix`: ², ³, %
* **상태**: `angle_mode_rad`(Deg↔Rad 토글).

## MainWindow (UI 컨트롤러)

* **UI 로드**(uic.loadUi), 디스플레이 바인딩(`le_expr`, `le_result`)
* **핸들러 자동 라우팅**: 버튼들을 스캔해 `_handlers` 구성 후, 모든 `clicked`를 공용 람다로 연결

  * 숫자/점/삼각·쌍곡은 선점(람다 기본인자로 캡처) → 나머지는 `id`의 꼬리 `tail`로 `do_<tail>`을 찾아 등록
* **UX 상태와 동작**:

  * `_pending_clear`: `=` 이후 첫 입력 정책 관리(Ans 시드/화면 클리어)
  * 암시적 곱셈(`_maybe_mul`), 함수머리 통삭제(DEL), 괄호 자동 닫기, 폰트 자동 축소 등

# 3) 입력 → 계산 → 출력 데이터 흐름

1. **버튼 클릭**
   `clicked` → `_handlers[name]()` 호출
2. **표시식 구축**

   * 숫자/점/사칙/괄호/π/후위연산/함수 입력 유틸들이 `le_expr` 텍스트를 누적 관리
   * 규칙:

     * 값 뒤 함수/π/여는 괄호면 `x` 자동 삽입(암시적 곱셈)
     * `%`, `²`, `³`는 **값 뒤에서만** 허용
     * `=` 직후 사칙/제곱은 **Ans 시드**, 함수/여는 괄호/π는 **새 식 시작**
3. **평가(`=`)**

   * `do_equal()`:

     * 괄호 자동 닫기 → 내부 기호 치환(x,×,÷) → `engine.evaluate_expr(...)`
     * 성공: `last_result` 갱신, 결과 포맷팅(`fmt_number`) 후 `le_result`에 표시
     * 실패: `"Error"` 표시
     * `_pending_clear = True`로 다음 입력 정책 준비

# 4) 파서/평가 원리 (엔진 내부)

* **토큰화(\_tokenize)**
  숫자(부동소수), 연산자 `+ - * /`, 괄호, 상수(`π`/`pi`), `Ans`, 함수 식별자(`sin`, `cosh` 등), 후위(`²/³/%`)를 **문자 단위 스캔**으로 토큰화(정규식 불사용).

* **단항 마이너스 보정(\_fix\_unary\_minus)**
  식 시작/연산자/왼괄호/함수 뒤의 `-x`를 `0 - x`로 바꿔 **통일된 이항 연산**으로 처리.

* **셔닝야드(\_to\_rpn)**
  중위식을 스택으로 후위표기(RPN)로 변환.
  우선순위: `* /` > `+ -`
  닫는 괄호에서 함수가 있으면 함수 토큰을 RPN에 배치. 후위연산(POST)은 토큰 순서대로 출력.

* **RPN 평가(\_eval\_rpn)**
  스택 계산:

  * `NUM` push
  * `CONST`: `ans`면 `last_result`(없으면 0), `pi`면 `math.pi`
  * `OP`(2항), `FUNC`(1항, 훅 호출), `POST`(1항, 훅 호출)
  * 스택에 최종 1개만 남아야 유효

이 구조 덕분에 **연산 정의를 바꾸지 않고도** 훅만 확장하면 기능을 쉽게 늘릴 수 있어.

# 5) 라우팅 설계 포인트

* **자동 매핑 규칙**
  버튼 id `btno_plus` → tail=`plus` → `do_plus` 메서드 검색
  → 있으면 `_handlers[name]=do_plus` 등록.

* **숫자/점/삼각·쌍곡 선점**
  `btnn_7`은 tail=`7`이라 `do_7`이 없으므로 자동 매핑이 실패함.
  그래서 **선점**으로 `lambda d=d: self._append_digit(d)`를 미리 매핑.
  삼각·쌍곡도 `do_sin` 대신 `_insert_func("sin")`로 공통 경로를 쓰기 때문에 선점.

* **late-binding 방지**
  클릭 연결은 `lambda _=False, obj=b: ...obj.objectName()` 꼴로 **루프 변수 캡처**.

# 6) UX 규칙(계산기스러움)

* **Ans 시드**
  `=` 직후에 `+ - x ÷ ² ³` 등은 자동으로 `Ans`로 이어 계산.
  반면 함수/여는 괄호/π는 **새 식 시작**.

* **암시적 곱셈**
  값 뒤 함수/π/여는 괄호가 오면 자동으로 `x` 삽입(표시만).
  실제 평가 때는 `*`로 치환.

* **DEL 특례**
  `sinh(`, `cos(` 같은 **함수 머리**는 한 번에 지움. 후위연산(`²/³/%`)은 1글자.

* **괄호 자동 닫기**
  `=` 시 남은 여는 괄호만큼 `)`를 자동으로 보충.

* **폰트 자동 축소**
  두 디스플레이(`le_expr`, `le_result`) 길이에 따라 Bold 48pt → `900//len`(최소 5)로 축소.

# 7) 확장/변경이 쉬운 이유

* **새 함수 추가**

  * 표시만 필요한 **입력 함수**: `btnf_newf` 버튼을 만들고 선점 매핑에 `"newf"`를 추가하거나, `do_newf` 대신 `_insert_func("newf")`를 쓰면 됨.
  * **계산 로직**: `EngineeringCalculator.apply_function`에 `"newf"` 분기만 추가.

* **새 상수 추가**

  * 토큰화는 영문 식별자를 `FUNC/CONST/ANS`로 구분하니, `"e"` 같은 상수는 `const_value`에만 추가.

* **새 후위 연산 추가**

  * 토큰화에서 해당 기호를 `POST`로 인정, `apply_postfix`에 구현.

* **새 버튼 추가**

  * id가 `btno_*`면 `do_<tail>`만 만들면 자동 라우팅.
  * 숫자/삼각류처럼 규칙에서 벗어나면 선점 딕셔너리에 1줄 추가.

# 8) 에러·안정성

* **평가 실패**(파싱 오류/0으로 나누기 등) 시 `"Error"` 표시, `last_result=None`.
* `%`, `²`, `³`는 **맥락 제약**(숫자/값 뒤)으로 사용자 실수 방지.
* `sender()` 대신 **명시 라우팅 테이블**을 쓰므로, 시작 시점에 대부분의 매핑 문제가 드러남(자동 보완 루프 + `callable` 체크).

# 9) 성능/간결성 트레이드오프

* 파서/평가는 O(n)이며 실제 사용 규모에서 충분히 빠름.
* 라우팅은 dict 조회 한 번, `getattr`도 초기 한 번만 수행.
* 정규식/외부 라이브러리 없이 구현해 **의존성 최소 + 가독성 유지**.
