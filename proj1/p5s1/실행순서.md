문제 1. 비밀번호 찾기

수행 과제

emergency_storage_key.zip 의 암호를 풀 수 있는 코드를 작성한다. 단 암호는 특수 문자없이 숫자와 소문자 알파벳으로 구성된 6자리 문자로 되어 있다.

암호를 푸는 코드를 unlock_zip() 이라는 이름으로 함수로 만든다.

암호를 푸는 과정을 출력하는데 시작 시간과 반복 회수 그리고 진행 시간등을 출력한다.

암호를 푸는데 성공하면 암호는 password.txt로 저장한다.

암호를 풀 수 있는 전체 코드는 door_hacking.py로 저장한다.

보너스 과제

암호를 좀 더 빠르게 풀 수 있는 알고리즘을 제시하고 코드로 구현한다.




주어진 파이썬 코드는 emergency_storage_key.zip 파일의 암호를 찾기 위한 고도화된 브루트포스(무작위 대입) 프로그램입니다. 특히, 멀티프로세싱과 ZipCrypto 헤더 검증이라는 최적화 기법을 사용하여 암호 해독 속도를 크게 향상시켰습니다.

🔍 코드 분석
이 코드는 크게 세 가지 주요 기능으로 나뉩니다.

1. ZipCrypto 헤더 기반의 빠른 검증 (ZipCryptoValidator 클래스)
핵심 원리: ZIP 파일이 암호화될 때, 압축 데이터 앞에 12바이트 길이의 암호화 헤더가 추가됩니다. 이 헤더의 마지막 12번째 바이트는 특정 검증값(check byte)입니다. 비밀번호로 이 헤더를 복호화했을 때, 마지막 바이트가 원래의 검증값과 일치하는지 확인하면 비밀번호가 맞는지 빠르게 추정할 수 있습니다.

구현:

ZipCryptoValidator: ZipCrypto 암호화 알고리즘을 모방하여 비밀번호로 3개의 키를 초기화하고, 이 키로 암호화 헤더를 복호화하는 로직을 담고 있습니다.

check_password_fast(): 12바이트 헤더를 복호화하여 마지막 바이트를 예상 값과 비교하는 함수입니다. 이 방법은 정확도 1/256으로, 수많은 틀린 비밀번호를 초기에 걸러내어 불필요한 전체 압축 해제 시도를 줄입니다.

2. 스마트한 비밀번호 생성 전략 (smart_password_generator())
문제: 암호는 '숫자와 소문자 알파벳으로 구성된 6자리 문자'라고 했습니다. 순수하게 모든 경우의 수를 무작위로 생성하면 시간이 매우 오래 걸립니다.

해결: 이 코드는 인간의 비밀번호 설정 경향을 고려한 smart_password_generator() 함수를 사용합니다.

'pass', 'test', 'admin' 등 자주 사용되는 시작 패턴을 먼저 시도합니다.

mars06과 같이 끝에 숫자가 붙는 패턴을 먼저 시도합니다.

마지막으로 순수 알파벳 패턴을 시도합니다.

효과: 이 전략은 mars06과 같이 흔한 패턴의 암호를 훨씬 빠르게 찾을 가능성을 높입니다.

3. 멀티프로세싱을 활용한 병렬 처리
문제: 단일 프로세스로 모든 경우의 수를 대입하면 시간이 오래 걸립니다.

해결: multiprocessing 모듈을 사용하여 여러 개의 독립적인 프로세스(worker_process_improved)를 동시에 실행합니다.

구현:

main() 함수에서 cpu_count()를 통해 시스템의 CPU 코어 수를 확인하고, Pool을 생성하여 워커 프로세스를 시작합니다.

worker_process_improved(): 각 워커는 smart_password_generator()를 사용하되, 인터리빙(Interleaving) 기법을 적용합니다. 이는 각 워커가 모든 경우의 수를 나눠서 맡는 대신, worker_id에 따라 특정 순서(예: 1번 워커는 1, 5, 9, ...번째 시도, 2번 워커는 2, 6, 10, ...번째 시도)를 번갈아 가며 시도하는 방식입니다.

Queue: Manager().Queue()를 사용하여 여러 프로세스가 동시에 접근할 수 있는 큐를 만들고, 한 워커가 비밀번호를 찾으면 이 큐에 결과를 넣어 다른 워커들이 작업을 중단하도록 신호를 보냅니다.

🚀 프로그램 실행 순서
main() 함수 시작:

프로그램 시작 메시지를 출력합니다.

find_zip_file() 함수를 호출하여 emergency_storage_key.zip 파일의 경로를 자동으로 찾습니다.

파일이 없으면 오류 메시지를 출력하고 종료합니다.

unlock_zip() 함수 실행:

시작 시간과 시스템 정보를 출력합니다.

get_zip_info() 함수를 호출하여 ZIP 파일에서 **암호화 헤더(12바이트)**와 **체크 바이트(check byte)**를 추출합니다. 이 정보는 이후 빠른 검증에 사용됩니다.

cpu_count()를 통해 사용할 워커(프로세스)의 수를 결정하고 출력합니다.

병렬 처리 시작:

multiprocessing.Pool 객체를 생성하여 여러 개의 워커 프로세스를 준비합니다.

pool.map_async(worker_process_improved, tasks)를 호출하여 각 워커에 작업을 할당하고 비동기적으로 실행합니다.

tasks에는 각 워커에게 필요한 정보(ID, 파일 경로, 헤더 정보 등)가 포함됩니다.

worker_process_improved() 함수 실행 (각 워커 프로세스):

각 워커는 smart_password_generator()를 사용하여 비밀번호 후보를 생성하기 시작합니다.

인터리빙 방식에 따라, 자신의 worker_id 순서에 맞는 비밀번호만 가져와서 테스트합니다.

생성된 비밀번호마다 ZipCryptoValidator().check_password_fast() 함수를 호출하여 빠른 헤더 검증을 수행합니다.

헤더 검증에 통과하면 실제 zipfile 모듈을 사용하여 전체 압축 해제를 시도합니다.

만약 압축 해제에 성공하면, 이는 올바른 비밀번호임을 의미합니다.

해당 워커는 찾은 비밀번호를 result_queue에 넣고 작업을 종료합니다.

메인 프로세스의 결과 대기:

메인 프로세스는 while not results.ready(): 루프를 돌며 result_queue를 지속적으로 확인합니다.

result_queue에 비밀번호가 들어오면, pool.terminate()를 호출하여 다른 모든 워커 프로세스를 강제 종료시킵니다.

루프를 빠져나와 최종 결과를 처리합니다.

결과 출력 및 저장:

비밀번호를 찾은 경우, 총 소요 시간과 함께 성공 메시지를 출력합니다.

password.txt 파일에 찾은 비밀번호를 저장합니다.

zipfile 모듈로 다시 한번 압축을 해제하여 파일 목록을 확인하는 최종 검증을 수행합니다.

비밀번호를 찾지 못했거나 오류가 발생한 경우, 해당 메시지를 출력하고 프로그램을 종료합니다.

. ZipCrypto 헤더 기반의 빠른 검증 (ZipCryptoValidator 클래스)

핵심 원리: ZIP 파일이 암호화될 때, 압축 데이터 앞에 12바이트 길이의 암호화 헤더가 추가됩니다. 이 헤더의 마지막 12번째 바이트는 특정 검증값(check byte)입니다. 비밀번호로 이 헤더를 복호화했을 때, 마지막 바이트가 원래의 검증값과 일치하는지 확인하면 비밀번호가 맞는지 빠르게 추정할 수 있습니다.

구현:

ZipCryptoValidator: ZipCrypto 암호화 알고리즘을 모방하여 비밀번호로 3개의 키를 초기화하고, 이 키로 암호화 헤더를 복호화하는 로직을 담고 있습니다.

check_password_fast(): 12바이트 헤더를 복호화하여 마지막 바이트를 예상 값과 비교하는 함수입니다. 이 방법은 정확도 1/256으로, 수많은 틀린 비밀번호를 초기에 걸러내어 불필요한 전체 압축 해제 시도를 줄입니다.



ZIP 파일 암호화 헤더와 빠른 검증 원리
ZIP 파일 암호는 ZipCrypto라는 알고리즘을 사용하며, 이는 32비트 키 3개를 이용해 데이터를 XOR 연산으로 암호화합니다. 이 키는 비밀번호를 기반으로 생성되며, 데이터 암호화와 복호화에 모두 사용됩니다.

1. 12바이트 암호화 헤더 생성
ZIP 파일이 암호화되면, 실제 압축된 데이터 앞에 12바이트 길이의 가짜 헤더가 생성됩니다. 이 헤더는 비밀번호로 복호화했을 때 예측 가능한 값을 가지도록 설계되었습니다. 이 헤더의 생성 과정은 다음과 같습니다.

3개의 키 초기화: ZipCrypto 알고리즘의 세 키(key_0, key_1, key_2)는 각각 고정된 초기값으로 시작합니다 (key_0=0x12345678, key_1=0x23456789, key_2=0x34567890).

비밀번호로 키 업데이트: 비밀번호의 각 바이트를 순차적으로 사용하여 3개의 키를 복잡한 수학 연산으로 업데이트합니다.

가짜 헤더 생성: 업데이트된 키를 사용하여 임의의 12바이트 데이터를 암호화합니다. 이 12바이트 중 마지막 12번째 바이트는 특별한 의미를 갖습니다.

Check Byte: 이 12번째 바이트를 Check Byte 또는 **Verification Byte**라고 부릅니다. 이 바이트의 값은 원래 파일의 CRC32 체크섬 값이나 수정 시간 정보의 일부에서 가져옵니다. 따라서 이 값은 암호화되지 않은 ZIP 파일 정보에서 미리 알 수 있습니다.

결론적으로, 암호화된 ZIP 파일에는 "비밀번호를 사용하여 복호화하면 특정 값(Check Byte)이 나와야 하는" 12바이트 헤더가 포함됩니다.

2. 빠른 암호 체크 방법
일반적인 브루트포스 공격은 매번 비밀번호를 대입해 전체 압축을 해제해 보아야 합니다. 이 과정은 매우 느립니다. 반면, ZipCrypto 헤더를 이용한 방법은 다음과 같습니다.

예상 Check Byte 추출: ZIP 파일의 압축되지 않은 헤더 정보에서 Check Byte 값을 미리 추출합니다.

12바이트 헤더 복호화: 대입할 비밀번호 후보를 사용하여 12바이트 암호화 헤더를 복호화합니다.

마지막 바이트 비교: 복호화된 헤더의 마지막 12번째 바이트가 미리 추출한 Check Byte와 일치하는지 확인합니다.

이 방법의 핵심은 **"전체 파일을 복호화할 필요 없이 12바이트만 복호화하여 비밀번호의 유효성을 1차적으로 판단"**하는 것입니다.

정확도: 12번째 바이트는 256가지 경우의 수(0부터 255까지)를 가집니다. 따라서 틀린 비밀번호가 우연히 올바른 Check Byte를 만들어 낼 확률은 1/256 입니다.

False Positive (오탐): 이 확률 때문에, 올바르지 않은 비밀번호인데도 헤더 검증을 통과하는 경우가 발생할 수 있습니다. 이를 False Positive라고 하며, 코드에서는 이 경우에 대비해 실제 압축 해제를 시도하여 최종 검증을 합니다. 하지만 대부분의 잘못된 비밀번호는 헤더 검증 단계에서 걸러지므로, 전체적인 속도 향상에 큰 기여를 합니다.

아닙니다, 주어진 코드에서는 zipfile 모듈이 제공하는 복호화 함수를 사용하지 않습니다.

대신, ZipCryptoValidator라는 클래스를 직접 구현하여 12바이트 헤더를 복호화하고 검증합니다.

🔑 왜 직접 구현했는가?
속도 최적화: zipfile 모듈의 extractall() 함수는 파일 전체를 복호화하는 기능만 제공합니다. 이는 비밀번호가 맞는지 확인하기 위해 12바이트 헤더만 복호화하는 것보다 훨씬 비효율적입니다. 수많은 비밀번호 후보를 테스트해야 하는 브루트포스 공격에서는 작은 차이가 엄청난 시간 절약으로 이어집니다.

헤더 검증의 목적: 코드의 목표는 단순히 압축을 푸는 것이 아니라, 빠르게 틀린 비밀번호를 걸러내는 것입니다. 이를 위해 12바이트 헤더를 복호화하는 로직만 별도로 구현하여 check_password_fast() 함수에 담았습니다. 이 함수는 zipfile 모듈을 통하지 않고도 비밀번호의 유효성을 1차적으로 판단할 수 있습니다.

최종 검증: check_password_fast() 함수로 헤더 검증에 통과한 소수의 후보 비밀번호에 대해서만 최종적으로 zipfile.ZipFile(zip_path).extractall()을 호출하여 실제 압축 해제를 시도합니다. 이는 False Positive(오탐)를 확인하고 최종적으로 올바른 비밀번호를 확정하기 위한 단계입니다.






암호화헤더 마지막바이트 56이 로컬파일헤더 CRC32체크섬정보 E7부분이 일치하면 암호가 풀렸다고 가정하는거야


아닙니다, 두 값이 일치하는 것이 아니라 12바이트 암호화 헤더를 복호화했을 때 나오는 마지막 바이트가 **로컬 파일 헤더의 check byte**와 일치하면 암호가 올바른 것으로 **"추정"**하는 것입니다.

🔍 정확한 비교 대상
로컬 파일 헤더의 check byte:

이 값은 암호화되지 않은 ZIP 파일의 메타데이터(CRC32 체크섬 또는 파일 수정 시간)에서 추출됩니다.

이 코드는 get_zip_info() 함수에서 CRC32 체크섬(0x7399E73A)의 상위 바이트인 0xE7을 **예상 check byte**로 미리 가져옵니다.

복호화된 암호화 헤더의 마지막 바이트:

비밀번호 후보로 12바이트 암호화 헤더를 복호화합니다.

복호화 결과로 나온 12바이트 중 마지막 12번째 바이트의 값을 확인합니다.

만약 일치한다면, 이는 암호가 맞을 확률이 높다고 판단하고 다음 단계인 전체 압축 해제를 시도하여 최종적으로 암호가 맞는지 확인합니다. 이 check byte는 zipfile 표준에 따라 crc32 >> 24 또는 (mod_time >> 8) & 0xFF를 사용합니다.

이러한 이유로, 이 코드는 헤더 검증에 통과한 후보에 대해서만 실제 zipfile 모듈을 사용하여 압축 해제를 시도하는 최종 검증 과정을 포함하고 있습니다. 이 최종 단계에서 오류가 발생하지 않아야만 암호가 완전히 올바르다고 확정할 수 있습니다.

네, 맞습니다. 결국 최종 체크는 zipfile 모듈의 압축 해제 기능을 사용합니다.

코드는 다음과 같은 2단계 검증 과정을 거칩니다.

1차 검증 (고속 필터링): ZipCryptoValidator 클래스를 사용해 12바이트 암호화 헤더를 복호화하고 check byte와 비교합니다. 이 과정은 매우 빠르지만, 오탐(False Positive)의 가능성이 있습니다.

2차 검증 (최종 확인): 1차 검증을 통과한 소수의 비밀번호 후보에 대해, zipfile.ZipFile.extractall() 함수를 호출하여 실제로 파일이 정상적으로 압축 해제되는지 확인합니다. 이 단계가 성공해야만 올바른 비밀번호로 최종 확정됩니다.

이러한 2단계 전략은 무작위 대입의 효율성을 극대화하기 위한 핵심적인 최적화 기법입니다.

def get_zip_info(zip_path):

"""ZIP 파일에서 암호화 헤더와 CRC 정보 추출"""

with open(zip_path, 'rb') as f:

data = f.read()


# ZIP 로컬 파일 헤더 찾기

pos = data.find(b'PK\x03\x04')

if pos == -1:

raise ValueError("유효한 ZIP 파일이 아닙니다")


# 헤더 파싱

pos += 4 # 시그니처 건너뛰기

version = struct.unpack('<H', data[pos:pos+2])[0]

pos += 2

flags = struct.unpack('<H', data[pos:pos+2])[0]

pos += 2


if not (flags & 0x1): # 암호화 플래그 확인

raise ValueError("암호화되지 않은 ZIP 파일입니다")


method = struct.unpack('<H', data[pos:pos+2])[0]

pos += 2

mod_time = struct.unpack('<H', data[pos:pos+2])[0]

pos += 2

mod_date = struct.unpack('<H', data[pos:pos+2])[0]

pos += 2

crc32 = struct.unpack('<I', data[pos:pos+4])[0]

pos += 4

comp_size = struct.unpack('<I', data[pos:pos+4])[0]

pos += 4

uncomp_size = struct.unpack('<I', data[pos:pos+4])[0]

pos += 4

name_len = struct.unpack('<H', data[pos:pos+2])[0]

pos += 2

extra_len = struct.unpack('<H', data[pos:pos+2])[0]

pos += 2


# 파일명과 extra 필드 건너뛰기

pos += name_len + extra_len


# 암호화된 헤더 12바이트

encrypted_header = data[pos:pos+12]


# Check byte 계산 (bit 3 확인)

if flags & 0x8: # Data descriptor 사용

check_byte = (mod_time >> 8) & 0xFF

else:

check_byte = (crc32 >> 24) & 0xFF


return encrypted_header, check_byte, crc32



get_zip_info 함수는 ZIP 파일의 암호 해독을 위해 필요한 핵심 정보를 추출하는 역할을 합니다. 이 함수는 ZIP 파일의 내부 구조를 직접 파싱하여 12바이트 암호화 헤더와 **예상 check byte**를 찾아냅니다. 이는 zipfile 모듈이 제공하지 않는 저수준의 정보이며, 브루트포스 공격의 효율성을 높이는 데 필수적입니다.

📜 ZIP 파일의 내부 구조
ZIP 파일은 여러 개의 **파일 엔트리(file entry)**로 구성되며, 각 엔트리는 로컬 파일 헤더(Local File Header), 암호화 헤더(선택적), 압축된 데이터, 그리고 데이터 디스크립터(선택적)를 포함합니다. get_zip_info 함수는 이 중 로컬 파일 헤더를 파싱합니다.

🔍 get_zip_info 함수 실행 단계
파일 읽기 및 시그니처 찾기:

with open(zip_path, 'rb') as f: data = f.read(): ZIP 파일을 이진(바이너리) 모드로 읽어 전체 내용을 메모리에 저장합니다.

pos = data.find(b'PK\x03\x04'): ZIP 파일의 모든 파일 엔트리는 PK\x03\x04라는 4바이트 시그니처로 시작합니다. 이 코드는 find() 함수를 이용해 파일에서 첫 번째 파일 엔트리의 시작 위치를 찾습니다.

로컬 파일 헤더 파싱:

시그니처 뒤에는 로컬 파일 헤더가 이어집니다. 이 헤더는 파일의 메타데이터(버전, 플래그, CRC32, 크기 등)를 담고 있으며, struct.unpack()을 사용하여 바이트 데이터를 의미 있는 값으로 변환합니다.

flags = struct.unpack('<H', data[pos:pos+2])[0]: 이 부분은 파일의 **플래그(flags)**를 읽습니다. 특히, flags & 0x1은 파일이 암호화되었는지 확인하는 비트 플래그입니다. 만약 이 비트가 켜져 있지 않으면 암호화되지 않은 파일로 간주하고 ValueError를 발생시킵니다.

crc32 = struct.unpack('<I', data[pos:pos+4])[0]: 파일 데이터의 CRC32 체크섬 값을 읽습니다. 이 값은 뒤에서 check byte를 계산하는 데 사용됩니다.

암호화 헤더 위치 계산:

로컬 파일 헤더는 고정된 길이를 가지지 않고, 파일명 길이(name_len)와 추가 필드 길이(extra_len)에 따라 그 길이가 달라집니다.

pos += name_len + extra_len: 이 코드는 파일명과 추가 필드를 건너뛰어 암호화 헤더의 시작 위치를 정확히 계산합니다.

encrypted_header = data[pos:pos+12]: 계산된 위치에서 12바이트를 읽어 암호화 헤더를 추출합니다.

Check Byte 계산:

if flags & 0x8: ZIP 파일의 압축 정보는 파일 데이터 뒤에 붙는 **데이터 디스크립터(Data Descriptor)**에 저장될 수도 있습니다. 이 플래그는 그 사용 여부를 나타냅니다.

if 블록 실행 시: flags & 0x8이 참이면, check byte는 파일 수정 시간(mod_time)의 상위 1바이트에서 가져옵니다 ((mod_time >> 8) & 0xFF).

else 블록 실행 시: 그렇지 않은 경우, check byte는 crc32 값의 상위 1바이트에서 가져옵니다 ((crc32 >> 24) & 0xFF). 이 코드는 crc32 값을 24비트 오른쪽으로 이동시켜 상위 8비트(1바이트)만 남기는 연산입니다.

값 반환:

마지막으로, 함수는 추출한 12바이트 암호화 헤더(encrypted_header), 계산된 예상 check byte, 그리고 파일의 crc32 값을 튜플 형태로 반환합니다. 이 값들은 이후 브루트포스 워커 프로세스에서 사용됩니다.

struct.unpack() 함수는 바이너리 데이터(바이트)를 특정 형식의 파이썬 값으로 변환하는 데 사용됩니다. <I와 <H는 그 변환 형식을 지정하는 포맷 문자열입니다.

struct.unpack()
역할: 이진 데이터를 구조체(struct) 형식에 따라 풀어내는(unpack) 기능을 합니다. zipfile과 같은 바이너리 파일을 다룰 때 필수적인 함수입니다.

사용법: struct.unpack(format, buffer) 형태로 사용하며, format은 데이터의 형식을, buffer는 변환할 이진 데이터(바이트)를 지정합니다.

< (리틀 엔디안)
설명: <는 리틀 엔디안(little-endian) 바이트 순서를 의미합니다. 리틀 엔디안은 데이터의 최하위 바이트(least significant byte)가 가장 낮은 메모리 주소에 저장되는 방식입니다.

예시: 정수 0x12345678을 저장할 때, 리틀 엔디안 방식에서는 78 56 34 12 순서로 저장됩니다. 대부분의 인텔 기반 시스템(Windows, macOS, 리눅스)에서 사용하는 기본 순서입니다.

I (부호 없는 4바이트 정수)
설명: I는 **부호 없는 4바이트 정수(unsigned integer)**를 의미합니다. 4바이트는 32비트에 해당하며, 0부터 4,294,967,295까지의 값을 표현할 수 있습니다.

코드에서의 역할: crc32 = struct.unpack('<I', data[pos:pos+4])[0] 코드는 현재 위치(pos)부터 4바이트를 읽어 리틀 엔디안 순서의 **부호 없는 32비트 정수(unsigned 32-bit integer)**로 변환하고, 그 값을 crc32 변수에 할당합니다. [0]은 unpack의 반환값이 튜플이기 때문에 실제 값을 가져오기 위한 인덱싱입니다.

H (부호 없는 2바이트 정수)
설명: H는 **부호 없는 2바이트 정수(unsigned short)**를 의미합니다. 2바이트는 16비트에 해당하며, 0부터 65,535까지의 값을 표현할 수 있습니다.

코드에서의 역할: version = struct.unpack('<H', data[pos:pos+2])[0]와 같은 코드에서는 현재 위치부터 2바이트를 읽어 **부호 없는 16비트 정수(unsigned 16-bit integer)**로 변환합니다. ZIP 파일 헤더의 버전이나 플래그와 같은 정보는 보통 2바이트로 표현되기 때문에 <H 포맷을 사용합니다.
